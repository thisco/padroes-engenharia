## O que fazer

Quando uma mudança altera o comportamento de um requisito `R<n>` de uma spec que já foi
arquivada, a spec não pode ficar como está: antes do merge, acrescente a ela uma seção
`## Adendo AAAA-MM-DD` que diz qual `R<n>` mudou e como ele passa a valer. Isso vale
principalmente para o hotfix, que costuma ir direto ao código sem passar por spec nova.

O motivo é que a spec arquivada é histórico, e não fonte de verdade viva
[ref:sdd-scaffold-sdd-processo], mas segue sendo lida por quem entra no projeto (é o custo do delta
que a ADR 0003 do portal registra). O desvio entre spec e código é apontado, numa síntese de terceiros,
como o principal problema prático do desenvolvimento orientado a spec [ref:field-study-xu]. Um
artigo sobre governança descreve a reconciliação como passo humano: uma pessoa resolve cada desvio, corrigindo o código ou
atualizando o desenho [ref:infoq-when-pays-off].

A decisão do portal é manter a spec como delta arquivado e histórico, e não como fonte de verdade
viva: a ADR 0003 (`docs/adr/0003-formato-de-spec-delta-arquivado.md`) escolhe o delta arquivado, e
a Fase 8 da skill muda o `Status` da spec para `arquivada` [ref:sdd-lifecycle]. Sem spec viva, o
substituto é o adendo à spec citada. A própria ADR 0003 lista o conflito entre um hotfix e um
delta arquivado como gatilho para reavaliar a spec viva, então adendos que se acumulam são o sinal
para reabrir essa decisão, com uma ADR nova.

## Como aparece quando falta

O hotfix noturno vai ao código, o teste novo passa, o PR é aprovado, e a spec continua dizendo o
contrário. Meses depois, quem lê a spec arquivada implementa a partir de um requisito que já não
vale, ou dá o código por errado. Não há erro nem teste quebrado: o desvio só aparece quando
alguém compara os dois.

## Como aplicar

1. No plano da mudança, liste numa seção `## Requisitos afetados` as specs e os `R<n>` cujo
   comportamento a mudança altera. O scaffold 1.7.0 não tem esse campo no modelo de plano: o aviso
   automático e a seção `Requisitos afetados` no Tier 1 (M5) estão previstos para o sdd-scaffold
   1.8.0 [ref:sdd-scaffold-spec-verificavel] e a ADR 0003 os mantém na Release 2. Até lá, acrescente
   a seção à mão.
2. Para cada spec citada, acrescente ao fim dela `## Adendo AAAA-MM-DD`, com o `R<n>` alterado,
   o comportamento novo e o plano da mudança. Não reescreva o texto aprovado do requisito nem
   o `Status`: o adendo é um acréscimo datado, e o resto da spec continua como foi aprovado.
3. Salve o script do Exemplo em `scripts/checar-requisitos-afetados.py`. Commite o plano e a spec
   com o adendo na branch e só então rode o script: ele compara o que está **commitado** (`git
   diff base...HEAD`), e não a árvore de trabalho. Ele lista as specs citadas por `Requisitos
   afetados` e avisa se alguma não está no diff ou está sem adendo novo. Se o commit do plano
   ainda não existe, a saída é `0 spec(s) citada(s), nenhum achado`, um verde que não confere nada.
4. Se o projeto não aceita trailer de coautoria nos commits, diga ao agente que a mensagem do
   commit sai sem ele: alguns harnesses o acrescentam por padrão.
5. Se o comportamento mudou mas nenhuma spec cobria o requisito, escreva o requisito numa spec
   nova (Fase 1 da skill, delta) em vez de um adendo [ref:sdd-lifecycle].

Se o time usa o Elephant-Goldfish Model, a skill `egm-drift-report` cobre outra ponta do mesmo
problema: ela lê cada design doc de uma pasta, procura o código que o documento cita e lista só as
divergências, sem descrever o que está de acordo, num arquivo `AAAA-MM-DD_DRIFT_REPORT.md`
[ref:egm-drift-report-skill]. Ela não corrige nada: a origem diz que quem escolhe entre atualizar o
documento ou o código é a pessoa, e recomenda rodá-la como ritual semanal, de
preferência na rotação de manutenção, se o time tem uma [ref:egm-getting-started]. A varredura é da pasta inteira contra o código atual, e não
do diff da branch [ref:egm-drift-report-skill], então ela complementa o adendo antes do merge, e
não o substitui.

## Exemplo

### Antes e depois

Um hotfix limita a observação do pedido a 200 caracteres. A spec arquivada diz que a observação é
"de texto livre" (`R1`). O plano declara o requisito afetado, e o script, rodado sobre a branch
sem alteração na spec, avisa:

```markdown
## Requisitos afetados

- `docs/specs/2026-10-05-observacao-no-pedido.md`: R1. A observação, antes de texto livre sem
  limite, passa a ser cortada em 200 caracteres.
```

```text
AVISO: docs/plans/2026-10-06-limite-da-observacao.md: a spec docs/specs/2026-10-05-observacao-no-pedido.md é citada em Requisitos afetados, mas não está no diff; acrescente a ela um '## Adendo AAAA-MM-DD'.
```

Depois, a spec ganha o adendo ao fim, sem tocar no texto aprovado, e nova rodada sai limpa:

```diff
+## Adendo 2026-10-06
+
+O hotfix da branch `fix/2026-10-06-limite-da-observacao` (plano
+`docs/plans/2026-10-06-limite-da-observacao.md`) altera o comportamento do **R1**: a observação
+deixa de ser texto livre sem limite e é cortada em 200 caracteres ao criar o pedido, porque o
+campo do banco não comporta mais que isso. O texto original dos requisitos acima ficou como foi
+aprovado; vale o que este adendo diz sobre o R1.
```

```text
Requisitos afetados: 1 spec(s) citada(s), nenhum achado.
```

### Para o agente

Prompt para a sessão que prepara o PR do hotfix:

```prompt
Aplique a prática P1-10 do portal de padrões de engenharia à branch atual, que contém um hotfix
descrito no plano {caminho do plano}.

1. Rode python3 scripts/checar-requisitos-afetados.py --base {base de comparação, main se eu não
   disser outra} e mostre a saída.
2. Para cada spec que o aviso apontar, leia a spec e o diff da branch, e diga em uma frase qual
   R<n> mudou de comportamento.
3. Acrescente ao fim de cada spec apontada a seção "## Adendo {AAAA-MM-DD}" com o R<n> alterado, o
   comportamento novo e o caminho do plano. Não altere o texto dos requisitos nem o Status da spec.
4. Faça um commit só com a spec, com a mensagem no formato docs(specs): ..., sem linha de
   coautoria nem outro trailer.
5. Rode o script de novo (ele compara o que está commitado) e mostre a saída; ela precisa sair
   sem aviso. Rode também {comando de testes} e mostre o resultado.
6. O único arquivo que você altera é a spec: não mexa no código, nos testes nem no plano.
```

## Como verificar

Não há mecanismo: a força é `orienta` e o campo `mecanismo` fica vazio. O aviso automático, que
conferiria `Requisitos afetados` no PR, está previsto para o sdd-scaffold 1.8.0 e não existe na
1.7.0 [ref:sdd-scaffold-spec-verificavel]. O script do Exemplo é um candidato que um time pode ligar
ao CI como aviso. O prompt acima roda o script no passo 4, antes do commit do passo 5: com o adendo
ainda sem commit o aviso continua, e a saída pedida (sem aviso) vem só depois do commit, na
rodada seguinte. Ele só confere o que o plano declara: não descobre um requisito afetado que o
plano esqueceu de listar, não lê o adendo para ver se ele descreve o comportamento certo, e não
vê o hotfix que ficou sem plano. Quem aprova o PR confere se a lista de requisitos afetados é
completa e se o adendo diz a verdade.
