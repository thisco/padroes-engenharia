## O que fazer

Escreva a spec de uma mudança Tier 2 como um delta: ela descreve a mudança e não o sistema
inteiro. É a regra da skill na Fase 1 [ref:sdd-lifecycle] e a frase do cabeçalho do modelo de spec
do scaffold [ref:sdd-scaffold-modelo-spec]. O conteúdo mínimo é o problema que dói, os requisitos
`**R<n>**`, cada um com ao menos um critério de aceite (Dado/Quando/Então ou EARS), e o que fica
fora do escopo [ref:sdd-lifecycle]. O que a mudança não toca não aparece na spec: quem precisa do
resto lê o código, a spec base e os deltas anteriores.

Esta é uma escolha de formato com alternativa conhecida. O OpenSpec também escreve deltas
(requisitos adicionados, modificados e removidos), mas os funde na spec principal ao arquivar a
mudança [ref:openspec-concepts]. O portal adota o delta sem a fusão: a spec vira histórico no
merge, e o que passou a ser permanente é promovido a steering ou a uma ADR. O portal escolheu não manter
uma spec viva: a spec de uma mudança é aprovada, implementada e arquivada. A ADR 0003, que mora no
repositório do portal (`docs/adr/0003-formato-de-spec-delta-arquivado.md`) e não no do seu projeto,
também registra o gatilho para reavaliá-la. A Thoughtworks descreve o mesmo caminho do delta como
adequado a sistemas existentes [ref:thoughtworks-radar-openspec].

## Como aparece quando falta

A spec nasce descrevendo o sistema: o que já existe, a arquitetura, o que não muda. Ela fica longa,
a revisão perde o foco, e ninguém sabe qual linha é a mudança. O custo é de proporção: num teste
com o Kiro, um bug pequeno virou quatro histórias de usuário e 16 critérios de aceite, e o autor
chamou a abordagem de marreta para quebrar noz [ref:bockeler-sdd-3-tools]. É um relato de uma
pessoa, e não um estudo, mas mostra o sintoma: o texto cresce mais do que a mudança.

O segundo sintoma é a spec que envelhece. Se ela descreve o sistema, alguém precisa mantê-la em
dia a cada mudança, e a Thoughtworks distingue justamente a spec que se mantém depois da tarefa
(spec-anchored) daquela escrita antes e usada no fluxo (spec-first) [ref:bockeler-sdd-3-tools]. Uma
descrição do sistema, sem dono, diverge do código.

## Como aplicar

1. Classifique a mudança (prática [P1-01](P1-01.html)). Spec é para Tier 2; Tier 0 e Tier 1
   seguem sem spec [ref:sdd-lifecycle].
2. Copie `docs/specs/MODELO-spec.md` para `docs/specs/AAAA-MM-DD-nome-curto.md` e troque o título
   pelo da mudança [ref:sdd-scaffold-modelo-spec].
3. Escreva a Motivação em poucas linhas: o problema que dói, não a história do sistema.
4. Escreva cada requisito como `**R1** comportamento observável`, com a linha `Critério` logo
   abaixo [ref:sdd-scaffold-modelo-spec]. Um requisito descreve o que a mudança entrega. O que
   continua como está não ganha requisito: vai para os não-objetivos, se precisar ser dito.
5. Reduza o Design proposto ao que muda: componentes tocados e contratos alterados. Não redescreva
   o que ficou igual.
6. Peça a aprovação a uma pessoa. O registro (`Status`, `Aprovado por`, `Aprovado em`) é gravado
   por quem aprova, ou a pedido dele [ref:sdd-lifecycle]. Marcar dúvida aberta é a prática
   P1-05, tratada à parte.

## Exemplo

### Antes e depois

Antes, a spec de uma mudança pequena abre descrevendo o sistema:

```markdown
## Motivação

O Sistema de Pedidos é composto pelos módulos de catálogo, carrinho, pagamento e entrega. O
catálogo guarda produtos e preços; o carrinho agrupa itens; o pagamento chama o gateway...
(duas páginas sobre o sistema, e a mudança aparece só no fim: "expor o desconto do pedido").

## Requisitos

R1. O sistema deve permitir consultar pedidos.
R2. O sistema deve calcular descontos.
```

Os requisitos descrevem o que o sistema já faz, não a mudança, e não têm critério. Depois, a spec é
o delta: o problema em quatro linhas, dois requisitos com critério e os não-objetivos. O arquivo
completo é a spec do MODELO-spec da 1.7.0, preenchida para a mudança "expor o campo `desconto` na
consulta do pedido":

### Para o agente

Prompt para redigir a spec como delta:

```prompt
Aplique a prática P1-04 do portal de padrões de engenharia: escreva a spec desta mudança como
um delta, que descreve só a mudança e não o sistema.

Mudança: {descrição da mudança, em uma ou duas frases}
Data de hoje: {AAAA-MM-DD}
Nome curto do arquivo: {nome-curto, em minúsculas com hífen}

1. Crie a branch feat/{AAAA-MM-DD}-{nome-curto} a partir da main.
2. Copie docs/specs/MODELO-spec.md para docs/specs/{AAAA-MM-DD}-{nome-curto}.md e preencha. Use
   só o que está na descrição acima; o projeto não tem código da aplicação para explorar. Não
   descreva o sistema nem o que não muda. Escreva cada requisito como "**R<n>** ..." com uma linha
   "Critério" em Dado/Quando/Então, e ponha em Não-objetivos o que fica de fora. Deixe o Status
   como "rascunho" e os campos "Aprovado por" e "Aprovado em" vazios: a aprovação é de uma pessoa.
3. Se faltar informação para um requisito, não invente: deixe [ESCLARECER: pergunta] no ponto e
   me diga quais são as perguntas.
4. Preencha o Threat-model ou escreva "não se aplica" com o motivo, nunca apague a seção.
5. Faça um commit só com a spec (docs(specs): ...) e rode python3 scripts/verificar_pr.py --base
   main. Mostre a saída.
6. Não altere nenhum outro arquivo.
```

## Como verificar

Não há mecanismo que confira se a spec é um delta: não existe regra automática para "descreve só a
mudança", porque o escopo é julgamento de revisão. O candidato mais próximo é o `verificar_pr.py`
do scaffold, que confere o que é mecânico: requisito `**R<n>**` válido, critério de aceite em cada
um e aprovação gravada em spec com status aprovada [ref:sdd-scaffold-verificar-pr]. Ele só avisa,
não bloqueia. Spec que passa sem achado pode ainda ser longa demais: a conferência de proporção é de
quem revisa. Sinal de alerta na revisão: requisito que ninguém pode falhar (descreve o que já
funciona) ou seção de motivação maior que os requisitos.
