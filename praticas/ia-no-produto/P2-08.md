## O que fazer

Trate o prompt e a configuração do modelo como artefato de entrega, com a mesma disciplina do
código. O guia de GenAIOps da Microsoft lembra que, numa solução generativa, o prompt é parte
central do que se governa, e que um bom ambiente de experimentação guarda as mudanças de prompt junto
com as saídas, para avaliar o experimento [ref:azure-genaiops-mlops]. Separe três camadas:

1. **Configuração versionada.** Prompt de sistema, ID do modelo e parâmetros (`max_tokens`,
   temperatura, esforço) num arquivo do repositório, com um campo `versao` que sobe a cada mudança. O
   ID do modelo é fixo: na API da Anthropic, todo ID de modelo é um snapshot fixo, e cada modelo tem
   uma data mínima de aposentadoria [ref:anthropic-models-overview]. Mudar o arquivo é uma MR que
   roda o eval (P2-05).
2. **Contrato selado em código.** O formato da saída, o guardrail e o tratamento de conteúdo externo
   (P3-05) ficam no código da aplicação, não no texto do prompt. O formato vai como schema: com
   structured outputs, a resposta segue o schema dado, sem JSON malformado nem campo obrigatório
   faltando [ref:anthropic-structured-outputs]. Ninguém muda o contrato editando o prompt.
3. **Contexto governável.** O que o negócio ajusta com frequência (glossário, exemplos, regras do
   domínio) pode morar fora do deploy, num banco ou numa ferramenta de prompts, desde que tenha dono,
   histórico, versão e o mesmo eval antes de valer em produção.

## Como aparece quando falta

O prompt está numa string no meio do código, o modelo é um apelido que o fornecedor troca e ninguém
sabe qual texto produziu a resposta de ontem. Alguém ajusta o prompt direto em produção para
resolver um caso e quebra outros, sem eval e sem como voltar. Ou o contrato mora no prompt ("responda
em JSON com as chaves...") e um ajuste de texto o desfaz. Sem structured outputs, o modelo pode gerar
JSON malformado ou faltar um campo obrigatório mesmo com o prompt bem escrito
[ref:anthropic-structured-outputs].

## Como aplicar

1. **Tire o prompt do código.** Mova o prompt de sistema para um arquivo em `ia/prompts/` e a
   configuração para `ia/config/<tarefa>.yml`, com `versao`, `modelo` (o `id` do catálogo da P2-03 ou
   o ID fixo do modelo), `parametros` e o caminho do prompt. O código lê esse arquivo; nenhum texto de
   prompt fica no código.
2. **Suba a versão a cada mudança** de prompt, modelo ou parâmetro, na mesma MR, e registre a versão
   em cada chamada (log ou traço), para saber qual versão produziu cada resposta.
3. **Rode o eval na MR.** A suíte da P2-05 roda contra a configuração nova; o limiar não se afrouxa
   para o pipeline passar.
4. **Feche o contrato no código.** Declare o schema da saída no código e mande-o à API; no Claude, o
   parâmetro é `output_config.format` [ref:anthropic-structured-outputs]. Valide a resposta contra o
   mesmo schema antes de usá-la.
5. **Governe o contexto que muda fora do deploy.** Se o contexto mora numa ferramenta de prompts,
   use versão e rótulo de ambiente. No Langfuse, por exemplo, cada versão ganha um ID, o rótulo
   `production` marca a versão servida por padrão, voltar atrás é mover o rótulo para a versão
   anterior, e rótulos protegidos, que restringem quem os muda, existem só nos planos Enterprise
   [ref:langfuse-prompt-version-control]. Num banco próprio, o equivalente é tabela com versão,
   autor, data e quem aprovou, com leitura da versão marcada como ativa.
6. **Troca de modelo é mudança de configuração**: nova `versao`, eval verde e, para produção, a
   promoção da P2-07. Acompanhe a data de aposentadoria do modelo [ref:anthropic-models-overview] e
   planeje a troca antes dela.

## Exemplo

### Antes e depois

Antes, prompt, modelo e formato estão no código:

```python
resposta = cliente.chat.completions.create(
    model="ultimo-modelo",
    messages=[{"role": "system", "content": "Classifique o pedido e responda em JSON com 'categoria'."},
              {"role": "user", "content": pedido}],
)
```

Depois, a configuração versionada em `ia/config/classificar.yml`:

```yaml
versao: 3
modelo: modelo-a-api             # id do catalogo-modelos.yml (P2-03)
prompt_sistema: ia/prompts/classificar.md
parametros:
  max_tokens: 512
  temperature: 0
```

E o contrato no código, que nenhuma edição de prompt muda:

```python
SAIDA = {"type": "object", "required": ["categoria"], "additionalProperties": False,
         "properties": {"categoria": {"enum": ["duvida", "reclamacao", "pedido"]}}}

config = yaml.safe_load(Path("ia/config/classificar.yml").read_text())
prompt = Path(config["prompt_sistema"]).read_text()
log.info("classificar", extra={"config_versao": config["versao"], "modelo": config["modelo"]})
```

### Para o agente

Prompt para tirar o prompt do código e versionar a configuração:

```prompt
Siga a prática P2-08 do portal de padrões de engenharia nesta aplicação, para a tarefa de modelo
{nome da tarefa}.

1. Liste os lugares do código com texto de prompt, nome de modelo ou parâmetro de modelo
   (model=, max_tokens, temperature, mensagens de sistema). Mostre a lista.
2. Mova o prompt de sistema para ia/prompts/{nome da tarefa}.md e crie
   ia/config/{nome da tarefa}.yml com versao: 1, modelo (o id do catálogo, se o projeto tiver
   catalogo-modelos.yml; senão o ID fixo do modelo, nunca um apelido), prompt_sistema e
   parametros com os valores que estavam no código.
3. Faça o código ler o arquivo de configuração e registrar config_versao e modelo no log de cada
   chamada. Não deixe texto de prompt no código.
4. Se o código pede um formato de saída no texto do prompt, declare o schema no código, valide a
   resposta contra ele e tire do prompt a instrução de formato. Não mude a lógica de negócio.
5. Rode os testes e a suíte de eval do projeto, se houver. Mostre a saída.
6. Faça um commit com a mensagem "refactor: prompt e configuração de modelo versionados (P2-08)".
```

## Como verificar

Não há mecanismo: a força é `orienta`. Para conferir à mão numa MR que muda prompt, modelo ou
parâmetro: o `versao` do arquivo de configuração subiu; o `modelo` é um `id` do catálogo (ou um ID
fixo); o eval rodou contra a configuração nova; e o diff não traz texto de prompt nem nome de modelo
no código. O verificador candidato é um script de `ci` que acusa a MR que altera um arquivo de
`ia/prompts/` ou `ia/config/` sem subir o `versao`, e literal de nome de modelo fora de `ia/config/`.
