## O que fazer

Depois de a aplicação entrar no ar, toda chave virtual dela tem um orçamento: um teto de gasto
em dólares (`max_budget`) e um período de renovação (`budget_duration`, como `30d`)
[ref:litellm-budgets]. Sem o teto, o limite padrão é nenhum [ref:litellm-budgets]. O gasto fica
registrado por chave, e o time do gateway o consulta para saber quanto cada aplicação consome
[ref:litellm-virtual-keys].

## Como aparece quando falta

Uma aplicação entra em laço, ou um teste de carga vai parar no gateway de produção, e a conta
do provedor sobe sem que ninguém saiba qual aplicação gastou. Um gateway de IA existe, entre
outras coisas, para gerenciar o uso de tokens e as cotas entre várias aplicações
[ref:azure-apim-ai-gateway]; a chave sem teto abre mão disso para aquela aplicação.

## Como aplicar

1. Peça ao time do gateway a chave com `max_budget` e `budget_duration`, uma por aplicação e por
   ambiente (P2-01), com o teto de homologação menor que o de produção. O teto do Exemplo (0,1
   dólar) é só para a demonstração.
2. O orçamento só é aplicado com banco: o proxy sem banco segue atendendo, mas não impõe o
   teto [ref:litellm-proxy-docker] [ref:litellm-budgets].
3. O gasto é calculado a partir do custo do modelo. Num modelo próprio ou simulado, declare
   `input_cost_per_token` e `output_cost_per_token` no `model_info` do `config.yaml`, como o
   Exemplo faz [ref:litellm-custom-pricing].
4. Na aplicação, trate a recusa por orçamento: ela volta como erro HTTP, e a aplicação mostra uma
   mensagem de limite e **não** tenta de novo em laço. No LiteLLM v1.104.0 a recusa foi um 422
   com `type` `budget_exceeded` (abaixo); a documentação descreve um 401 com
   `ExceededTokenBudget` [ref:litellm-budgets]. Confira o código na versão que você usa.
5. Consulte o gasto por chave com `/key/info`, que traz `spend`, `max_budget` e
   `budget_duration` [ref:litellm-budgets]. Na execução da curadoria o gasto gravado apareceu
   com atraso: logo após a recusa o relatório mostrou 0, e segundos depois, o valor certo.
6. Para ser avisado antes de estourar, defina um `soft_budget` na chave. O alerta de orçamento
   é enviado pelo Slack, com `SLACK_WEBHOOK_URL`, `budget_alerts` em `alert_types` e
   `alerting: ["slack"]` [ref:litellm-alerting]. O Exemplo não executa o alerta, que depende de
   um webhook.
7. Rode `verificar-orcamento.sh` periodicamente: ele lista as chaves sem orçamento.
8. Ao desativar a aplicação, apague a chave (`/key/delete`, abaixo) ou peça isso ao time do
   gateway.

## Exemplo

### Antes e depois

Antes, a chave nasce sem teto e o gateway atende sem limite. Depois, a chave nasce com um teto
e um período:

```bash
curl -sf "$GW/key/generate" -H "Authorization: Bearer ${LITELLM_MASTER_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"key_alias": "app-teste-hml", "models": ["simulado"], "max_budget": 0.1, "budget_duration": "30d"}'
```

Crie uma pasta `gateway-teste/` e copie para ela, lado a lado, os seis arquivos de
[`exemplos/P2-06/`](../exemplos/P2-06/). Com Docker e Python 3 instalados, rode dentro da pasta:

```bash
echo "LITELLM_MASTER_KEY=sk-teste-$(openssl rand -hex 16)" > .env
echo "GATEWAY_PORT=4001" >> .env
docker compose up -d
set -a; . ./.env; set +a
export AI_GATEWAY_URL="http://localhost:${GATEWAY_PORT:-4000}"
until curl -sf "$AI_GATEWAY_URL/health/liveliness" >/dev/null; do sleep 3; done
export AI_GATEWAY_KEY="$(bash emitir-chave.sh app-teste-hml simulado 0.1)"
python3 -m venv .venv && . .venv/bin/activate && pip install openai==3.24.0
python gastar.py
bash relatorio-gasto.sh "$AI_GATEWAY_KEY"
```

Cada chamada custou 0,031 dólar neste modelo simulado. A quarta passou, com o gasto em 0,093, e a
quinta foi recusada (saída real do LiteLLM v1.104.0, com o pacote `openai` 3.24.0):

```text
chamada 1: ok
chamada 2: ok
chamada 3: ok
chamada 4: ok
chamada 5: UnprocessableEntityError: Error code: 422 - {'error': {'message': 'Budget has been exceeded! Key=app-teste-hml (sk-...4zdw) Current cost: 0.12400000000000849, Max budget: 0.1', 'type': 'budget_exceeded', 'param': None, 'code': '422'}}
```

O relatório de gasto por chave, rodado logo em seguida e de novo alguns segundos depois:

```text
app-teste-hml: gasto 0.0000 de 0.1
app-teste-hml: gasto 0.1240 de 0.1
```

### Para o agente

Regra curta para o `AGENTS.md` do projeto:

```markdown
A chave do gateway (AI_GATEWAY_KEY) tem orçamento. Trate o erro de orçamento excedido com uma
mensagem de limite e sem tentar de novo em laço. Nunca peça nem use a master key do gateway.
```

Prompt para ver o orçamento estourar e registrar o gasto:

```prompt
Verifique o orçamento de uma chave virtual no gateway de teste desta pasta, seguindo a prática
P2-06 do portal de padrões de engenharia. O gateway de teste está em gateway-teste/ e todos os
comandos abaixo rodam dentro dele.

1. Crie o arquivo .env com LITELLM_MASTER_KEY=sk-teste- seguido de 32 caracteres hexadecimais
   aleatórios (openssl rand -hex 16) e GATEWAY_PORT={porta}. Confirme com git check-ignore .env
   que ele está no .gitignore.
2. Suba o gateway com docker compose up -d e espere o health check passar:
   until curl -sf "http://localhost:{porta}/health/liveliness" >/dev/null; do sleep 3; done
3. Carregue o .env (set -a; . ./.env; set +a), exporte AI_GATEWAY_URL=http://localhost:{porta} e
   AI_GATEWAY_KEY="$(bash emitir-chave.sh {alias} simulado {orcamento})". Crie um venv
   (python3 -m venv .venv), ative-o e rode pip install openai==3.24.0.
4. Rode python gastar.py e mostre a saída.
5. Rode bash relatorio-gasto.sh "$AI_GATEWAY_KEY". O gasto é gravado com atraso: enquanto a
   saída trouxer "gasto 0.0000", espere 3 segundos e rode de novo, no máximo 30 vezes. Mostre a
   última saída.
6. Emita uma segunda chave, sem orçamento, e rode o verificador:
   curl -s "$AI_GATEWAY_URL/key/generate" -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" -d '{"key_alias": "app-sem-teto"}' > /dev/null
   bash verificar-orcamento.sh
   Mostre a saída, que precisa acusar app-sem-teto (saída 1). Depois apague essa chave:
   curl -s "$AI_GATEWAY_URL/key/delete" -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" -d '{"key_aliases": ["app-sem-teto"]}'
   e rode bash verificar-orcamento.sh de novo, que precisa sair com 0. Mostre a saída.
7. Crie ORCAMENTO.md na raiz do repositório com uma tabela de uma linha (alias da chave,
   orçamento em dólares, gasto em dólares, chamadas aceitas) e, abaixo, o type e o code da
   resposta de recusa, copiados da saída do passo 4. Não escreva nenhuma chave nem a master key
   no arquivo.
8. Faça um commit só com ORCAMENTO.md, com a mensagem
   "docs: registro de orçamento da chave virtual de teste (P2-06)". Não altere outro arquivo.
9. Derrube o gateway com docker compose down -v.
```

## Como verificar

Não há mecanismo no CI, e a prática só orienta: o orçamento mora no gateway, que o impõe a cada chamada
[ref:litellm-budgets]. O verificador candidato lista as chaves virtuais sem orçamento e sai com 1
se achar alguma:

<!-- incluir: exemplos/P2-06/verificar-orcamento.sh -->

Com uma chave criada sem `max_budget`, ele acusa; depois de apagá-la (`/key/delete`, confirmado
pela execução da curadoria), sai com 0:

```text
app-sem-teto
P2-06: chave virtual sem orçamento (acima).
```

```text
P2-06: todas as chaves virtuais têm orçamento.
```

O que ele não cobre: se o teto é adequado ao uso, se o alerta chega a alguém, a chave de outro
gateway e o gasto que o gateway não enxerga (uma chamada direta ao provedor, que a P2-01 proíbe).
