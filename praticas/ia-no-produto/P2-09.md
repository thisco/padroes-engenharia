## O que fazer

Chamada a modelo que leva segundos ou minutos não roda dentro do request HTTP de quem pediu. A API
valida o pedido, põe o trabalho numa fila, responde `202 Accepted` com o endereço de um recurso de
status e devolve a conexão; um worker separado tira o trabalho da fila, chama o modelo e grava o
resultado; o cliente consulta o status até o fim. É o padrão Asynchronous Request-Reply, que o
Azure Architecture Center descreve para o trabalho de back-end que não cabe na espera de uma
resposta síncrona [ref:azure-async-request-reply].

O worker processa em lotes, e o lote é dimensionado pela conta: **tamanho do lote × custo unitário
(o tempo por item, p95 medido) × margem < timeout** de quem segura o trabalho (a visibilidade da fila, o tempo máximo
do job ou do worker). A conta é do portal; o tempo por item vem da medição do próprio projeto.

## Como aparece quando falta

O endpoint chama o modelo e espera. Na maior parte das APIs a resposta volta em cerca de 100 ms, e o
trabalho que leva segundos ou minutos não pode esperar para responder
[ref:azure-async-request-reply]. Quando uma falha de rede perde a resposta, o cliente, que não
distingue resposta perdida de pedido não recebido, repete o `POST` que o servidor já aceitou
[ref:azure-async-request-reply], e o modelo roda e é pago de novo. No worker, um lote grande demais
passa do timeout da fila: a mensagem não apagada antes do fim da visibilidade volta a ficar visível
e outro consumidor a processa de novo [ref:aws-sqs-visibility-timeout], e o lote recomeça do zero a
cada tentativa, até a mensagem ir para a fila de mensagens mortas, se houver uma
[ref:aws-sqs-visibility-timeout].

## Como aplicar

1. **Aceite e responda 202.** Valide o pedido antes de enfileirar e responda com erro, como `400`,
   se ele for inválido; se for válido, responda `202` com o cabeçalho `Location` apontando o status e
   `Retry-After` com a espera sugerida para a próxima consulta [ref:azure-async-request-reply]. O
   `202` diz que o pedido foi aceito para processamento e que ainda não terminou, e a RFC recomenda
   que a resposta descreva o estado do pedido e aponte um monitor de status [ref:rfc-9110].
2. **Endpoint de status.** Responda `200` com o estado (`pendente`, `executando`, `concluido`,
   `falhou`, `cancelado`) enquanto o trabalho anda e, ao terminar, `303 See Other` para o recurso do
   resultado; em falha, grave o erro no recurso [ref:azure-async-request-reply]. Defina por quanto
   tempo o status e o resultado ficam guardados.
3. **Repetição sem duplicar.** Aceite uma chave de idempotência no pedido (`Idempotency-Key`): se a
   chave já existe, devolva o status existente em vez de enfileirar de novo; para cancelar, ofereça
   `DELETE` no recurso de status [ref:azure-async-request-reply].
4. **Dimensione o lote.** Meça o p95 do tempo de uma chamada ao modelo no worker. Escolha o lote para
   que `lote × p95 × 1,2` fique abaixo do timeout de quem segura o trabalho, e escreva essa conta
   como teste (o Exemplo mostra). Numa fila com visibilidade, ajuste o timeout ao tempo máximo de
   processamento e estenda-o durante o processamento, se preciso; no Amazon SQS, o padrão é 30
   segundos, a extensão é pelo `ChangeMessageVisibility` e o teto é de 12 horas, acima do qual a
   documentação sugere o AWS Step Functions ou quebrar a tarefa em passos menores
   [ref:aws-sqs-visibility-timeout].
5. **Mensagem que falha sempre** vai para uma fila de mensagens mortas, para não circular para sempre
   na fila principal [ref:aws-sqs-visibility-timeout].
6. **Lote que pode esperar horas** pode ir para a API de lote do provedor, pelo gateway (P2-01), se
   ele a expuser. Na da Anthropic, o lote tem até 100.000 pedidos ou 256 MB, a maior parte termina em
   menos de uma hora, expira se não terminar em 24 horas, custa 50% do preço padrão, e o estado se
   acompanha por `processing_status` [ref:anthropic-message-batches].

## Exemplo

### Antes e depois

Antes, o endpoint espera o modelo:

```python
def post_classificacao(pedido):
    resultado = modelo.classificar(pedido["texto"])  # 20 s a 3 min
    return 200, {}, resultado
```

Depois, o endpoint enfileira e responde 202; o worker faz o trabalho:

```python
def post_classificacao(pedido, chave_idempotencia):
    if not pedido.get("texto"):
        return 400, {}, {"erro": "texto obrigatório"}
    tarefa = tarefas.obter_ou_criar(chave_idempotencia, estado="pendente")
    if tarefa.nova:
        fila.enviar({"tarefa": tarefa.id, "texto": pedido["texto"]})
    return 202, {"Location": f"/tarefas/{tarefa.id}", "Retry-After": "5"}, {"estado": tarefa.estado}
```

E a conta do lote vira teste, com o p95 medido pelo projeto:

```python
TIMEOUT_VISIBILIDADE_S = 300  # o da fila
P95_POR_ITEM_S = 4.0  # medido no worker, com o modelo do catálogo
LOTE = 50


def test_lote_cabe_no_timeout():
    assert LOTE * P95_POR_ITEM_S * 1.2 < TIMEOUT_VISIBILIDADE_S
```

```prompt
3. Crie o endpoint de status: 200 com o estado enquanto não termina, 303 para o resultado quando

5. Escreva um teste que confere que lote × p95 por item × 1,2 fica abaixo do timeout da fila, com

   "feat: trabalho de modelo fora do request (P2-09)".
```

## Como verificar

Não há mecanismo: a força é `orienta`. Para conferir à mão: o endpoint que chama modelo responde
`202` com `Location` e `Retry-After`; o status responde `200` enquanto não termina e `303` no fim; a
mesma `Idempotency-Key` não enfileira de novo; e há um teste com a conta do lote contra o timeout. O
verificador candidato é um script de `ci` que acusa chamada ao cliente do modelo dentro de função de
rota HTTP, mas a distinção entre rota e worker depende do framework, e por isso ele não existe ainda.
