Uma trilha, não um trilho

O portal diz onde o time precisa chegar em cada etapa. Como chegar lá fica com o time: as skills são caminhos possíveis, nossas ou de terceiros, e nenhuma é a oficial.

Marco: prática com mecanismo, vale em qualquer caminho Caminho: skill que ajuda a chegar ao marco
Minha recomendação

O portal mapeia marcos; as skills são caminhos

  1. Cada etapa se define pelo que precisa ser verdade ao sair dela.

    São as práticas que já temos (P1-01, QLD-01, P1-09…). O mapa lista os marcos de cada etapa e, para cada passo, as skills que ajudam a chegar lá, com "bom quando" e "cuidado". Nenhuma leva selo de oficial. É o mesmo formato das práticas: o que fazer, como aparece quando falta, como verificar.

  2. O que é inegociável fica no mecanismo, não na skill.

    Tier classificado, aprovação registrada, veredito por requisito, segredo fora do repositório e migration intocada viram hook ou verificador pelo motor de harness. Assim valem com qualquer caminho, e é isso que deixa a trilha livre: o time escolhe a skill, e o marco confere o resultado.

  3. Ofereça trilhas prontas como exemplo, não como receita.

    Três combinações completas que já funcionam (guiada, enxuta e disciplinada), mais "monte a sua". Quem está começando escolhe uma pronta; quem já sabe o que quer combina por passo.

  4. No projeto, uma skill por passo.

    O portal mostra várias; o projeto instala uma. Duas skills de TDD instaladas juntas disputam o acionamento e dão instruções que se contradizem. O scaffold pergunta qual trilha usar e instala só ela.

  5. Cada skill externa passa pela curadoria como ferramenta.

    Entrada em ferramentas/ com o campo etapa, versão fixada em componentes.yml e status avaliar. Ela só sobe para adotar com caso interno ou cenário do laboratório (otimizacao/) provando que funciona em PT-BR com os nossos marcos.

Isto muda uma decisão anterior. Tínhamos fechado a sdd-lifecycle 4.0 como "gates mais mapa". Com a ideia de trilha, eu faria diferente:
  • o mapa passa a ser o portal;
  • os gates vão para o mecanismo;
  • a sdd-lifecycle 3.x continua como está e vira a trilha guiada, uma opção entre outras.
Assim, nenhuma versão major é necessária agora. Essa mudança depende de você confirmar.

Para decidir

Atritos que a curadoria precisa resolver

Onde a spec é gravada

O to-spec e o code-review do Matt publicam num tracker; o setup aceita a opção "Other", e o scaffold pode entregar um docs/agents/issue-tracker.md apontando para docs/specs e docs/plans. O superpowers grava em docs/superpowers/, mas respeita a preferência do projeto.

Idioma

As três coleções são em inglês, e o template do to-spec traz títulos como "Problem Statement". O laboratório mede se o AGENTS.md basta para a spec sair em PT-BR, antes de qualquer skill subir para adotar.

Instruções que se contradizem

Refatorar fica fora do laço (MP), o código escrito antes do teste é apagado (SP), refatorar é a 3ª fase do laço (QLD-01). Cada trilha pronta precisa ser coerente por dentro, e a "monte a sua" mostra esses avisos.

Origem que muda

As três coleções mudam toda semana. Versão fixada, revalidação pelo revisar_ate e nada de PR para a origem: o SCOPE.md do Matt fecha propostas de skill nova.
